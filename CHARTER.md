# **MuLTItool Forge Project Charter**

## **1\. Mission Statement**

**MuLTItool Forge** is a collaborative open-source community dedicated to developing, sharing, and maintaining LTI-compliant tools that address functional gaps in enterprise Learning Management Systems (LMS). We empower universities to move faster than vendor roadmaps and address their custom needs by building high-quality, educator-focused solutions.

The enterprise LMS on campus has become monolithic in many ways. It is mission-critical, and oftentimes difficult, if not impossible, to modify or enhance directly. Much of the innovation around niche teaching and learning needs or emerging technologies has shifted toward LTI app development, since these tools can be added or removed as needed without disrupting the enterprise system. Institutions developing their own custom apps often find themselves operating in silos, building things that work locally but that may already have been developed at other institutions with similar needs. 

MuLTItool Forge seeks to connect these disparate teams of developers and provide a space for them to work together in a standards-based environment where they can contribute and share openly across institutions. We want to create a space where the collective code is refined and sharpened \- or “forged,” if you will, into a more elegant and effective instrument \- so that it is more easily consumed by other institutions and in other LMS environments. **The product of the project is not a single tool or software application, but rather a collection of curated, open, LMS-agnostic learning tools.**

## **2\. Core Objectives**

* **Bridge the Gap:** Create production-ready tools for features missing or under-optimized in platforms like Canvas, Blackboard, Brightspace, Moodle, or Sakai.  
* **Standards-First:** Adhere strictly to 1EdTech LTI (Learning Tools Interoperability) standards to ensure cross-platform compatibility.  
* **Open Source:** All project code released under an [OSI approved Open Source License](https://opensource.org/licenses).  
* **Collaborative Efficiency:** Reduce "reinventing the wheel" by allowing one university to build a solution and others to contribute to and sustain it.  
* **Security & Accessibility:** Ensure every tool meets rigorous institutional privacy requirements and accessibility standards.  
* **Collective Stewardship & Public Good:** Promote the collective imperative of higher education by acting as responsible financial stewards who prioritize shared, open resources over isolated, siloed development.

## ---

**3\. Governance & Roles** 

See GOVERNANCE.md for additional information.

MuLTItool Forge operates under a meritocratic model led by the **Project Management Committee (PMC)**.

| Role | Responsibility |
| :---- | :---- |
| **Project Management Committee (PMC)** | The primary steering body. Responsible for the project's strategic direction, approving new sub-projects, and voting on core membership. |
| **Community Manager** | Facilitates communication between institutions, manages onboarding for new contributors, and organizes community calls or events. |
| **Release Manager** | Oversees the versioning and distribution pipeline. Ensures that code meets quality benchmarks before being tagged for stable release. |
| **Maintainers** | Technical leads with "write" access to specific repositories; responsible for code review and merging PRs. |
| **Contributors** | Developers, IDs, or admins from any institution providing code, documentation, or bug reports. |
| **Advisory Board** | Instructional designers and faculty who provide feedback on pedagogical needs. |

## ---

**4\. Guiding Principles**

* **Open by Default:** All code is licensed under an OSI approved open source license.  
* **Vendor Neutral:** Tools should be designed to work across any LMS that supports LTI standards. (Note: If LMS specific APIs are needed to extend current LTI specs, the goal is to provide APIs for multiple LMSs.)   
* **Documentation is Code:** A tool isn’t finished until it has clear deployment guides and a README that a non-dev admin can understand.  
* **Institutional Privacy:** Tools must prioritize student data privacy and adhere to FERPA/GDPR principles by design.

## ---

**5\. Roadmap & Success Metrics**

### **Initial Focus Areas**

1. **Admin Utilities:** Bulk actions, custom dashboards, system utilities, etc.  
2. **Engagement Tools:** Niche interactive, workflow, or content-creation tools.

### **Success Metrics**

* Number of unique institutions contributing code or documentation.  
* Number of active deployments across the Higher Ed ecosystem.  
* Reduction in "custom development" hours for participating universities.
